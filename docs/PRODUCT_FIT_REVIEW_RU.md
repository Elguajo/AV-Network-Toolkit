# Насколько AV Network Toolkit решает исходную задачу

Сверка от 31 октября 2026 года. Ветка `main`, исходный HEAD `648f207`. Основание: [исходная идея](ORIGINAL_IDEA_SUMMARY_RU.md), текущий код и записанная проверочная документация. Незакоммиченная Phase 06 находится в разработке; эта сверка не подтверждает её готовность. Живые сетевые и браузерные проверки в этой задаче NOT RUN.

## Вывод

Выбранная основа соответствует задаче: проект хранит сетевые настройки ноутбука и ссылки оборудования, которые можно использовать при возвращении на объект. Однако нынешний сценарий ещё нельзя считать полностью готовым удобным переключателем проектных Ethernet-пресетов. До приёмки нужно закрыть отдельное применение профиля без устройства, проверить практический переход из DHCP в изолированную AV-подсеть и выполнить испытания на Windows. Разрешённое владельцем хранение паролей — дополнительное требование, которого текущий формат пока не поддерживает.

Девять этапов описывают подходящее направление, но само выполнение их списка без проверки этих пользовательских сценариев не доказывает решение задачи. Процент готовности по числу этапов здесь неинформативен.

## Три разрыва, которые нужно сохранить в плане

**IDEA-01 — применение проекта без веб-устройства.** В `ProjectViewModel` есть команды создания/редактирования/сохранения профиля, но нет команды его применения. `ApplyAndOpenCommand` в устройстве требует выбранную запись и связанный профиль. Поэтому наличие автономного базового переключателя и наличие переносимого проекта пока не образуют полностью единый сценарий. Не следует создавать фиктивное устройство с URL только ради применения профиля. Это пробел покрытия исходной потребности, а не изменение кода в данной сверке.

**IDEA-02 — исходное состояние ноутбука.** Для AV-пусконаладки важно начинать с обычного DHCP, включая случай отсутствия DHCP-сервера на отдельном коммутаторе. Сейчас новый механизм консервативно отклоняет DHCP без пригодного адреса, автоматическую APIPA, сложные/неизвестные состояния, дополнительные адреса/маршруты, Static/automatic DNS и /31–/32. Эти ограничения были согласованы ради сохранности конфигурации. Они могут блокировать именно рабочее подключение к оборудованию; исправление требует отдельного контракта и тестов, а не снятия проверок вслепую. Наличие API для такого изменения не считается доказательством поддержки.

**IDEA-03 — учётные данные.** Владелец явно разрешил хранить пароли в JSON в этом чате (ADR-024). Запрет на само хранение паролей больше не является требованием конечного продукта. Текущая реализация v1 при этом остаётся прежней: ручное добавление `password` не создаст поддерживаемую запись; неизвестное поле будет отклонено. Помещать пароль в notes или URL как обход ограничения не является реализацией функции.

## Требование к паролям: что считаем готовым

FR-13: пользователь может по желанию сохранить учётные данные устройства в переносимом JSON проекта. Минимальный предлагаемый интерфейс — отдельные логин/пароль в записи устройства, скрытый пароль и явные команды просмотра/копирования. Этот интерфейс предложен для реализации; разрешение хранить пароли уже получено и не требует повторного согласования.

Критерии реализации:

1. Пароль необязателен. Старые проекты без учётных данных продолжают открываться; точные версия формата и миграция определяются до изменения схемы. Новая программа не теряет пароль при Open → Edit → Save As → Open, в том числе при кавычках, Unicode и пробелах в значении.
2. Пользователь понимает, что обычная строка в JSON читается любым обладателем файла. Копии проекта и резервные `.bak` тоже будут содержать пароль; это переносимое хранение, а не обещание шифрования.
3. Пароль скрыт по умолчанию и не участвует в поиске, группировке, обычном предпросмотре URL, диагностике, сетевом recovery-журнале или сообщениях ошибок. Доступ к нему — отдельное действие. Для копирования нужно определить срок и безопасное условие очистки буфера до реализации.
4. Примерные проекты, тесты и репозиторий содержат только вымышленные значения. Право сохранить пароль в личном файле не разрешает публиковать реальные пароли в Git, логах или результатах тестов.
5. Сохранение/открытие проекта не выполняет вход на устройство и не меняет сеть. Open и Apply & Open передают браузеру только проверенный URL; пароль не встраивается в userinfo/query/аргументы процесса. Обход TLS, хранение токенов и автоматическая авторизация не включены в это разрешение.
6. Изменение/удаление пароля сохраняется предсказуемо; старый пароль может оставаться в ранее созданных резервных копиях, что должно быть видно в описании хранения. Не обещать удаление из всех копий после правки одного файла.

Это критерии будущей функции, а не отчёт об уже написанном коде.

## Как доказать, что задача решена

Приёмка должна пройти на одноразовой изолированной Windows-среде, с отдельным разрешением на живые действия:

1. Подготовить проект с несколькими разными подсетями, профилем без шлюза и каталогом устройств. Сохранить, закрыть, открыть: вручную повторно вводить настройки не требуется.
2. Выбрать любой проектный профиль и применить его без устройства/URL. Показать именно выбранный адаптер и фактические IP/маску/шлюз/DNS; другие интерфейсы и IPv6 сохраняются.
3. Отдельно проверить поддержанный переход из офисного DHCP в изолированную AV-сеть, включая согласованную обработку отсутствия DHCP, APIPA и DNS. Блокировка должна объяснять конкретную причину и дальнейшее действие.
4. Открыть полный URL панели отдельно и через Apply & Open. При отказе UAC/ошибке применения браузер не открывается; при успешной передаче URL не заявляется успешная авторизация или доступность устройства.
5. Восстановить поддерживаемое исходное состояние или явно включить DHCP, сравнить состояние и отчёт. Убедиться, что несовместимые состояния не маскируются под успешный откат.
6. После реализации FR-13 открыть проект на другом ПК и получить сохранённый пароль отдельным действием без повторного ввода. Без пароля тот же сценарий остаётся работоспособным.

Основная мера успеха — повторное подключение к сохранённому объекту без ручного переписывания сетевых параметров, URL и, когда сохранены, паролей. Контрольный критерий — отсутствие неожиданного изменения другого NIC, потери настроек или выдачи неподтверждённого результата за успех. Замеры времени и живая приёмка пока NOT RUN; облачная телеметрия для этого не требуется.
